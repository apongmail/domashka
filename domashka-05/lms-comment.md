# Коментар для LMS — ДЗ 5

Роботу виконав на macOS: замість `ip addr` використав `ifconfig`, а
Linux-утиліту `conntrack` запустив у Docker Desktop.

## Основні результати

| Пункт | Результат |
|---|---|
| `172.20.0.0/22` | мережа `172.20.0.0`, broadcast `172.20.3.255`, хости `172.20.0.1–172.20.3.254`, **1022 хости** |
| 4 рівні підмережі | `172.20.0.0/24`, `172.20.1.0/24`, `172.20.2.0/24`, `172.20.3.0/24`; по 254 хости |
| Моя адреса | `192.168.8.230/24`, підмережа `192.168.8.0/24`, broadcast `192.168.8.255` |
| IPv6 | лише link-local `fe80::/10`; глобальної адреси й маршруту немає |

Розрахунок `/22`: маска `255.255.252.0`, на хости залишається 10 біт,
тому `2^10 − 2 = 1022`. Для чотирьох `/24` позичаємо ще 2 біти:
`4 × 256 = 1024` адреси — весь початковий блок без дірок і перетинів.

IPv6 перевірив не лише через `ifconfig`: пряме з'єднання з реальною
AAAA-адресою Google повертає `No route to host`. Водночас `dig AAAA`
працює через IPv4 DNS-транспорт — це показує, що DNS-записи й транспортна
IPv6-зв'язність є незалежними речами.

Цікавий природний експеримент: посеред курсу я сховав ноутбук за новим
роутером, який сам чіпляється по Wi-Fi до старого — вийшов каскад із
подвійним NAT (`192.168.8.0/24` → мережа старого роутера → провайдер).
Перегнав усі перевірки: публічна адреса й ASN не змінились, а глобального
IPv6 як не було, так і немає (до ноутбука тепер не долітає навіть ULA
старого роутера). Отже, обмеження саме на боці провайдера — скільки
NAT-рівнів не додавай, IPv6-префікса згори ніхто не видає.

## Опціональна частина

- **VLSM:** web `172.20.0.0/24`, app `172.20.1.0/25`, db
  `172.20.1.128/26`; решта — резерв. Для AWS окремо врахував 5
  зарезервованих адрес у кожній підмережі та різницю між NACL, Security
  Groups і route tables.
- **conntrack:** у Docker побачив NAT-відповідність
  `172.17.0.2 → 192.168.65.3` зі станами `TIME_WAIT` і `[ASSURED]`.
- **A vs AAAA:** порівняв 32-бітні A та 128-бітні AAAA-записи Google;
  прямий IPv6-конект не проходить через відсутність маршруту.
